# 通用奖励数据与展示规范（设计草案）

更新：2026-09-16。

状态：数据与展示第一阶段已接入。`RewardDefinitionSO` 定义资源，`RewardEntry` 定义发放方式和数量/秒数，`RewardDataSO` 定义奖励包，`RewardChestStyleSO` 定义宝箱品质和外观。`SeasonPassRewardDefinition` 已成为奖励包 SO；通行证原 25 档配置已迁为 49 份奖励包引用。原 `RewardData` 类型、旧道具清单字段和新旧模式开关已移除，另外 7 份旧奖励包及其调用方已迁移。`RewardSlotView` 自动选择单项/宝箱，两条轨道分别绑定。限时权益实际发放、存档和消费仍待游戏接收器接入。

2026-09-16 产品规则：用户已确认限时无限道具也在领取成功后立即生效；限时效果按现实时间运行，离线和暂停继续计时；同一效果重复领取累加剩余时长。这些计时规则不由奖励 View 执行。下文的运行时入账/权益机制仍属后续设计，以本节及末尾验证记录区分当前能力。

## 0. 当前配置入口

1. 打开 `Assets/GameMain/Activities/SeasonPass/ScriptableObjects/Config/SchoolPass202609.asset`，在每个 Tier 的 `Free Reward` / `Premium Reward` 中选择 `SeasonPassRewardDefinition` SO；空引用表示该位置没有奖励。
2. 双击奖励包，在“奖励清单”里选择资源、`AddQuantity` 或 `UnlimitedUse`，填写数量或持续秒数。通行证现有奖励包位于 `ScriptableObjects/Rewards/SchoolPass202609/`，例如 `Tier_05_Premium.asset`。
3. 每包的“宝箱品质 / 外观”引用 `RewardChestStyleSO`。现有四份位于 `Assets/GameMain/ScriptableObjects/Reward/Chests/`：`Chest_Common`、`Chest_Rare`、`Chest_Epic`、`Chest_Legendary`；编辑品质 SO 的名称、等级和 sprite 可统一调整外观。
4. 一项显示资源图标和数值，两项及以上显示指定宝箱，零项隐藏内容；单项忽略宝箱样式。当前按配置条目显示，不自动合并重复条目。奖励数量 `×10` 仍算一项。
5. 资源 SO 保存普通图标和可选无限图标；无限奖励的文本带 `∞`。当前使用 `h / m / s` 时长缩写，例如 `∞ 30m`。缺图项明确显示资源名和数值。当前示例的金币、额外步数、炸弹、锤子、钻头图标待美术绑定，未冒用其他奖励图片。
6. 通行证奖励包与资源定义可分别复用；包的修改在下次界面绑定/打开时读取。运行中的正式活动修改奖励内容应同时考虑已有领取记录，不能用更换 SO 的方式重发同一领取 ID。

当前数量发放仍通过既有活动网关：公共金币要求 `common` 范围，游戏道具要求与已安装主玩法范围一致并有接收能力；范围不符或无限方式保持不可领取。新模型不代表已经实现任意子游戏的统一库存和限时权益。

创建菜单：`Assets/Create/GF/Activity/Season Pass/Reward Bundle`、`Assets/Create/GF/Common/Reward/Resource`、`Assets/Create/GF/Common/Reward/Chest Style`。通用奖励包使用 `GF/Common/Reward/Bundle`；所有奖励包统一编辑 `RewardEntry` 清单，没有新旧模式开关。

现有配置迁移入口沿用 `Tools/Activity/Season Pass/Install Config And Validate UI`。安装器仅在配置不存在时创建默认 25 档；再次运行会保留已编辑的档位和奖励包。迁移保留旧资源键、顺序及请求单位；无限生命在 SO 内保存 1800 秒，旧请求仍为 `minute / 30`。没有旧品质数据的多项包先明确指定普通样式，这是迁移初值，作者可逐包更换。

### 0.1 金币与道具数量如何处理

`RewardEntry.Amount` 是本次奖励的增量，SO 不保存玩家余额。例如金币 `300` 表示领取后增加 300，道具 `3` 表示增加 3 个；双倍领取只在发放时计算乘 2，不修改 SO。

| 奖励 | 配置 | 实际写入 |
| --- | --- | --- |
| 金币 | 资源键 `currency.money`、范围 `common`、`AddQuantity`、数量 | `RewardQuantityUtility` 累加 `GameEntry.SaveData.Money`；现有 `SaveDataStore.Money` setter 写入 Setting 并调用保存 |
| 提示 / 洗牌 / 加时道具 | 键分别为 `prop.hint / prop.shuffle / prop.add_time`；范围明确填写所属 `GameMode` 名称；`AddQuantity`、数量 | 对应游戏管理器的 `CanGrantProp / TryGrantProp`，由游戏更新自己的库存与存档 |
| 无限生命 / 无限道具 | 资源、`UnlimitedUse`、秒数 | 数量接收器拒绝；待限时权益接收器完成后启用 |

活动网关与旧领奖页面现在共用 `RewardQuantityUtility`。领奖页先检查整包的资源、作用域、数量、倍率及金币容量，再开始逐项增加；没有接收器时不会播放成功领取流程。活动网关要求单位为 `count`，保留其已有领取 ID 和回执机制。该工具只负责数量接入，不提供跨多个存档的事务保证，后续可靠发奖仍需处理第 3.6 节的部分成功与重试边界。

当前金币存档与道具接口使用 `int`，配置数值乘倍率不得超过 `int.MaxValue`，金币还会检查增加后的总余额。模板没有安装具体玩法；`SubGameManagerComponent` 的道具接收方法默认返回 `false`。新产品需要在所属游戏实现真实库存和持久化，不能仅配置一个资源 SO 就视为已能发放。没有经济系统的游戏只配置道具即可。

原 7 份道具奖励包引用 `ScriptableObjects/Reward/Definitions/Game_Hint.asset`，其范围明确为模板的 `Game`；导入其他具体游戏时应改为该游戏自己的资源定义。当前源码已不提供旧 `RewardData` 构造方式，外部旧代码需要改为 `RewardEntry`。

## 1. 范围与已确认需求

面向当前长期维护的 GF 模板，为活动、任务、排行等入口提供一致的奖励展示方式。

- 一个奖励入口只有一项奖励时，显示奖励图标和数值。
- 一个奖励入口含多项奖励时，显示宝箱；点击宝箱打开 `RewardTooltipView`，展开真实奖励清单。
- 宝箱有不同价值档次，对应不同外观。
- **用户已确认：无限生命奖励领取成功后立即开始计时，不存入背包等待使用。**
- **用户已确认：限时无限道具同样领取成功后立即生效；限时效果在离线、暂停期间继续计时；剩余 10 分钟再次领取 30 分钟后变为 40 分钟。**
- 奖励模型覆盖金币、道具数量、普通生命数量、限时无限生命、限时无限道具。每个产品/游戏只接入实际支持的资源与发放方式；没有经济或生命系统的游戏不需要实现这些能力。
- 当前提供四档宝箱样式，由奖励包显式引用；不假定已有数值经济换算表。

## 3. 奖励内容与数值定义

### 3.1 资源与发放方式分别定义

**资源**表示金币、某个道具或某种生命资源；**发放方式**表示增加数量，或在一定时间内使用该资源免消耗。无限生命与无限道具共用后者。

| 资源分类 | 具体资源示例 | 发放方式 | 数值意义 | 展示示例 |
| --- | --- | --- | --- | --- |
| Currency | 金币 | `AddQuantity` | 数量 | 金币图标 + `×300` |
| Item | 提示道具 | `AddQuantity` | 数量 | 提示图标 + `×3` |
| Life | 生命资源 | `AddQuantity` | 数量 | 生命图标 + `×5` |
| Life | 同一种生命资源 | `UnlimitedUse` | 持续秒数 | 生命图标 + `∞` + `30分钟` |
| Item | 同一种提示道具 | `UnlimitedUse` | 持续秒数 | 提示图标 + `∞` + `30分钟` |

因此不继续为每一种道具新增 `InfiniteHint / InfiniteHammer` 枚举，也不把 `TimedEffect` 与金币、道具、生命并列为资源种类。资源分类只服务配置筛选和展示，真正可发放的组合由注册能力决定；金币不会因为同属奖励就自动获得“无限使用”能力。

UI 组件接收已解析的图片、数值文本及无限标记。数量和无限奖励共享资源身份，但保留不同的发放语义；不能因图标相同而合并。

### 3.2 数据归属

| 对象 | 内容 | 持有者 |
| --- | --- | --- |
| `RewardDefinitionSO : DisplayConfigSO` | 资源的稳定键、所属范围、资源分类、名称和图标；无限外观可单独配置或使用 `∞` 标记。当前沿用 `displayName`，名称本地化尚未接入 | 公共资源或所属子游戏的配置目录；复用基类 `id / displayName / sprite` |
| `RewardEntry` | `Definition`、`GrantMode`、正整数 `Amount`；发放方式决定 Amount 是数量还是秒数 | 奖励包中的一项；纯配置数据 |
| `RewardDataSO : IdOnlyConfigSO` | 有序 `RewardEntry` 清单和 `RewardChestStyleSO` 引用；承担奖励包职责 | 活动档位、任务、排行等来源；保留原资产 ID/GUID |
| `SeasonPassRewardDefinition : RewardDataSO` | 通行证奖励包 SO，复用通用奖励字段和 Inspector | 每档免费/高级位置分别引用；原内嵌对象仅作为隐藏的迁移来源 |
| `RewardDataBaseSO` | 继续持有各业务的奖励包引用；不作为玩家余额或限时状态容器 | 现有公共配置入口 |
| 运行时发奖请求 | 玩家身份、已解析的资源范围、不可变奖励明细、领取唯一标识；不携带可修改的 SO 状态 | 原业务模块创建，由接收适配器处理 |
| `RewardItemViewData` | 已解析图标、格式化文本、可选说明 | 纯 C# 展示转换逻辑，运行时生成 |
| 领取状态 | 是否解锁、是否可领取、是否已领取、是否处理中 | 原活动或业务模块，独立于宝箱皮肤与奖励静态定义 |
| 限时权益记录 | 对应玩家、资源范围、资源键的到期 UTC 时间及发奖去重记录 | 资源所属的存档模块；不写回 SO，也不挂在 UI 上 |

`RewardDefinitionSO` 在此表示可被奖励的资源。不同包可以引用同一资源，分别配置数量或无限时长。Inspector 根据 `GrantMode` 显示“数量”或“时长（秒）”；若提供分钟输入辅助，最终仍只保存一份规范化秒数。第一版不增加可自由组合的触发方式、计时方式和叠加策略字段，统一使用用户已确认的规则。

Inspector 配置示例：

```text
RewardDataSO
  Entries
    - Definition: GameA_Hint   GrantMode: AddQuantity   Amount: 3
    - Definition: GameA_Hint   GrantMode: UnlimitedUse  Amount: 1800
  ChestStyle: Chest_Rare（品质与图片由该 SO 持有）
```

这里是两项奖励：实际增加 3 个提示道具，同时获得 30 分钟免消耗。数量库存与限时权益各自保存，无限期间普通道具仍可入账。

配置引用与活动的外部键值数据是两种输入方式，通过显式适配器汇入同一规范化模型，不在同一条配置里重复维护两份奖励身份。保留当前活动 `ResourceKey / Unit / Amount` 的兼容读取；例如 `effect.unlimited_life / minute / 30` 明确映射为指定生命资源的 `UnlimitedUse / 1800秒`。不会把旧资源键当作新的资源分类，也不会从名称或图标猜测映射。

展示目录通过既有 `CustomConfigComponent` / 配置加载流程接入，或由页面显式传入。子游戏专用图标仍位于所属子游戏资源域，通过显式映射解析；公共 UI 不根据当前打开的活动或类名猜测归属。

### 3.3 单位和格式

- 数量使用正整数，内部保留准确值。默认统一为 `×300`、`×2`；若需要大数缩写，由统一格式器控制，详情保留完整数值。
- 时长建议以秒作为新通用模型的计算单位；旧 `minute` 配置经明确转换进入展示模型，旧源配置与发奖请求不在 UI 中改写。
- 示例：旧配置 `effect.unlimited_life / minute / 30` 对应 1800 秒，展示 `30分钟`，不能展示 `×30`。
- 时长格式由本地化格式器决定，支持分钟、小时、天；中间值保留剩余单位，例如 90 分钟显示 `1小时30分钟`。
- 时长奖励卡展示“本次获得的时长”。领取后剩余时间属于生命系统的运行状态，不通过奖励卡文本反向推算。
- 无限生命与无限道具使用可区别于数量奖励的图标或 `∞` 标记；发放方式决定数值格式。
- 领取成功才激活效果。点击预览、刷新列表、播放宝箱动画都不能启动计时。
- 现实时间、立即生效、剩余时长累加已经确认，具体规则见 3.5。
- 数量奖励只接受数量单位，时长奖励只接受已声明的秒/分钟等时间单位。外部数据的未知单位、非正数、转换溢出必须在发奖前拒绝；不能只检查资源键。

### 3.4 不同游戏按能力接入

1. 资源身份包含明确的所属范围（公共或具体游戏）和资源键。游戏 A 的提示与游戏 B 的提示可以使用相似图标，但库存、到期时间和接收器按范围隔离。
2. 每个产品/游戏显式注册它支持的资源，以及每个资源支持的发放方式。注册组合可以是“只有数量道具”“数量道具 + 限时无限道具”或“金币 + 道具 + 生命”。
3. `SaveData` 存在、类型枚举中有金币、UI 能显示生命，都不足以说明该游戏支持对应奖励。启用目录与实际接收器两者必须匹配。
4. 公共金币只有在产品明确启用共享钱包时才注册为公共范围；游戏独有资源使用其游戏范围。既有 `profile` 表示接收玩家，不直接等同于资源归属。
5. 目标游戏在生成领取请求时确定并保持稳定。旧配置若按主玩法发放，通过明确的旧配置映射绑定到该主玩法；不在异步回调、切换场景或重试时重新读取 `CurrentGameMode` 改变收件目标。
6. 奖励包在展示和领取前分别校验，且必须整包通过资源、方式、单位、数值、数量上限和接收器状态检查。存在不支持的项时报告配置问题，禁止领取；不能跳过该项后宣称整包成功。
7. 活动复用时，由配置装配选择适合该游戏的奖励包。当前游戏没有金币时，不在 UI 内临时删除金币或自动换成道具；预览与实际发放使用同一份解析结果。

公共代码负责定义、解析、校验和展示。具体游戏提供数量入账及使用/扣费适配；没有生命系统的游戏不安装生命接收器。

### 3.5 限时无限效果：已确认规则与建议边界

**已确认的产品规则：**

- 无限生命和无限道具都在领取成功后立即生效。
- 使用现实经过时间，离线、暂停、返回菜单、切换游戏均继续消耗时长。
- 同一效果再次领取累加剩余时长；不同资源的效果各自计时。

核心计算以秒为单位，采用绝对 UTC 到期时间：

```text
有效：nowUtc < expiresAtUtc
剩余：max(0, expiresAtUtc - nowUtc)
追加：newExpiresAtUtc = max(nowUtc, oldExpiresAtUtc) + awardedSeconds
```

例如 10:00 领取 30 分钟，10:10 再领 30 分钟，到期时间变为 11:00。10:20 退出、10:50 返回，仍剩 10 分钟；到期时刻本身已失效。每次加法先检查溢出；若以后需要产品时长上限，应单独明确上限及超限补偿规则，不静默截断已承诺的奖励。

**建议采用的使用边界，随本方案确认：**

| 场景 | 处理规则 |
| --- | --- |
| 点击宝箱、展开提示、刷新页面 | 纯展示，无领取请求，也不激活或延期 |
| 业务领取提交成功 | 更新数量/到期记录并通知界面；开始时间由成功提交决定，与动画结束时间无关 |
| 无限权益有效且普通库存为 0 | 在游戏原有解锁、可操作、冷却等条件满足时允许使用 |
| 无限权益有效且普通库存大于 0 | 本次资源消耗为 0，普通库存保留 |
| 实际使用道具或扣生命 | 在游戏业务的扣费提交点再次查询权益，不能只依赖按钮显示的倒计时 |
| 操作被拒绝、目标无效或动作取消且尚未提交 | 沿用该游戏原有失败规则；不因为点击过按钮而额外扣数量 |
| 已被业务接纳的动作播放中到期 | 本次动作沿用接纳时的消耗决定，下一次动作重新检查 |
| 效果到期 | 使用已有库存和原扣费规则；界面还原数量展示，库存为 0 时回到原补充入口 |
| 相同资源的其他活动再发无限时长 | 汇入同一玩家/资源范围/资源键的权益，按剩余时长累加 |
| 关闭页面或活动结束 | 关闭界面订阅；已领取的权益按自己的到期时间继续有效 |

这里的无限生命指指定生命资源的免消耗权益。关内血量、受伤、失败判定与“进入关卡扣生命还是失败扣生命”由具体游戏决定；接入生命玩法时必须明确对应扣费点。当前模板的 `HealthBoxUI` 不足以确定该语义，不能直接用它实现所有游戏的无限生命。

### 3.6 发奖、存档和重复触发

- SO 只保存本次奖励的定义和时长。玩家的到期时间、已处理的领取 ID 属于运行时存档。
- 同一领取 ID 的双击、重复回调、超时重试、重启恢复只能延长一次。相同 ID 对应不同奖励或不同目标时判定冲突。
- 两次不同的领取同时到达时，按同一资源的最新到期记录串行提交，避免两次都读取旧时间而丢失其中一次累加。
- “领取成功”要求接收方确认数量/权益状态及去重记录可靠保存。完整预校验只避免已知错误，并不能代替保存事务。
- 当前活动接收器先写 `Pending`，再逐项发放；某项失败后写 `Failed`，重试可重新遍历清单。前面已到账的数量存在重复发放风险。它也没有把余额、时长与回执作为同一持久化提交，因此不能直接增加一个“延长时间”分支就视为接入完成。
- 后续运行时接入优先使用接收方能保证的共同提交边界；需要跨接收器时，必须提供逐项去重和可恢复的提交记录，并明确整包状态。尚不能保证的混合奖励包不启用限时领取。已经执行但保存结果不明的情况保持待核对，不能按普通失败重新加时。
- 启用限时奖励前，必须验证“发奖写入后、回执写入前崩溃”等恢复路径；部分提交不能向页面返回整包成功，也不能提前激活尚未确认到账的权益。
- 到期记录由资源所属存档持有，与活动实例寿命分离；不同玩家和不同游戏隔离。跨玩家奖励需有真正对应的余额存储，不能仅把当前活动回执的 `ProfileId` 当作现有全局余额已经隔离的证明。

**时间与生命周期：**通过显式传入的时钟读取时间，可复用现有活动时钟适配思路；公共奖励规则不依赖具体活动。当前 `LocalActivityClock` 使用设备 UTC，只能提供本地估计，不能宣称可防改时间；需要服务端权威时间的产品再接入对应适配。

显示界面启用时读取剩余时间，在需要显示倒计时时按秒刷新，禁用时取消刷新订阅；使用提交点始终实时校验。通过绝对到期时间恢复离线状态，不为每条奖励启动永久协程，也不依靠每帧写存档维持计时。

### 3.7 旧数据迁移边界

- 保留 `RewardDataSO` 的奖励包职责、现有资产 GUID/ID 和 `RewardDataBaseSO` 的业务引用，不为改模型批量重建 SO。
- 原 `RewardData.propType / Count` 已通过一次性编辑器操作迁为资源定义和 `AddQuantity`。原类型、旧字段和兼容分支已删除；`PropType` 仍服务实际游戏接口，枚举数值未改变。
- 先完成读取适配与影响资产的调用方清点，再执行可重复的编辑器迁移；迁移前后比较每包条目、数量、顺序和引用。未知道具映射应报告并停止该资产的迁移，不能默认映射为 Hint。
- `RewardChestView`、`RewardTooltipView`、领奖页、排行预览、宝箱事件和道具页都已切到 `RewardEntry`。旧外部样例的 C# 调用需要同步更新；不再保留另一份可发放的道具清单。
- 现有活动 `minute` 转秒只发生在明确的读取适配边界。保持原领取请求/回执的旧指纹兼容；新增范围/发放方式需要版本化，不能让已有领取记录失效后再次到账。
- 商店的去广告、任务的解锁/经验不强行转换成数量道具或无限道具。它们保留自己的已有入口；未来需要统一时再定义相应发放操作和验证。

## 4. 单项与宝箱的选择规则

对每个奖励入口单独判断；通行证的免费轨道和高级轨道分别判断，不能把两条轨道合成一个宝箱。

| 展示条目数 | 汇总入口 | 点击行为 |
| --- | --- | --- |
| 0 | 隐藏奖励内容入口 | 无 |
| 1 | 单项图标 + 数值 | 默认纯展示，不承担领取 |
| 2 项及以上 | 指定档次的宝箱图标 | 预览清单 |

- 道具 `×10` 仍是一项奖励。
- 同一资源、发放方式、单位、作用域且声明可相加的奖励可以合并显示。例如金币 200 + 金币 300，展示金币 `×500`；提示 `×3` 与提示无限 `30分钟` 保留为两项。
- 合并只作用于展示副本，保持首个出现位置。UI 不改写原发奖清单、数量、回执指纹或业务快照。
- 限时效果能否合并取决于效果自身的叠加规则，不能只因图标相同就相加。
- 宝箱外部默认不显示模糊的 `×N`，避免把清单项数误解成可领 N 个箱子。
- `RewardTooltipView` 和领奖明细属于展开视图，始终排列单项奖励，不再次把多项折叠成宝箱。
- 此规则用于奖励汇总入口。商品详情或其他本身已经展开的奖励明细，直接复用单项组件排列清单。

固定奖励组合先完整列出内容。本轮不引入随机掉落、概率宝箱、自选奖励或嵌套宝箱；以后需要时应新增明确的业务定义和对应预览规则。

## 5. 宝箱价值档次与外观

### 5.1 建议四档

| 建议档次 | 建议代号 | 含义 |
| --- | --- | --- |
| 普通 | Common | 基础价值奖励组合 |
| 稀有 | Rare | 中等价值奖励组合 |
| 史诗 | Epic | 高价值奖励组合 |
| 传说 | Legendary | 最高价值档次的奖励组合 |

四档是建议产品定义，不是现有 `ChestSkinType` 的别名。现有通用宝箱皮肤可作为候选资源，由配置显式建立映射，不按颜色、数组索引或旧枚举序号推断等级。

### 5.2 价值档次与活动主题分别配置

- `RewardChestStyleSO.Tier` 表达价值等级；继承的 `displayName / sprite` 提供名称和图片。
- 奖励包只引用品质/外观 SO，避免在包里同时维护一份可能不一致的等级和图片。后续需要开箱动画时再扩展该样式配置。
- 同一档次可使用默认或活动主题外观。首胜、连胜是活动来源/主题，不另占价值等级。
- 页面、预览入口和领奖动画共用这份映射，避免同一个奖励包在不同地方显示不同等级。
- 主题资源由活动自己持有；公共配置只持有通用皮肤，公共代码不引用某个具体活动类。

### 5.3 第一阶段建议显式配置

奖励包作者根据产品经济价值选择档次，并遵循统一配置说明。显示组件只读取结果。

自动计算可作为后续编辑器辅助校验：

```text
ValueScore = Σ（规范化后的奖励数值 × 对应资源单位的价值权重）

普通：0 < ValueScore < A
稀有：A ≤ ValueScore < B
史诗：B ≤ ValueScore < C
传说：ValueScore ≥ C
```

金币、道具、无限生命分钟不能直接相加。权重、A/B/C 必须由目标产品的经济配置给出；不同子游戏不假定共用一套兑换价值。缺少估值映射时应报告不能估值，不能静默按零价值或最低档处理。

目前项目没有已核实的这套换算表，本文不杜撰阈值。第一阶段只保存显式档次，不同时引入未经确认的自动计算结果。配置了一个奖励包后，它的实际内容由清单决定，不能根据“稀有箱”反向生成奖励。

- 点击另一个宝箱时，立即替换内容与锚点；条目数减少时隐藏多余项。
- 再次点击同一个宝箱可关闭；点击弹层外部关闭；打开的同一次点击不能立即关闭弹层。
- 每个页面最多同时显示一个奖励提示框，由页面明确持有实例，不增加全局单例。
- 弹层挂在页面适当的上层容器，避免被 ScrollRect / RectMask 裁切；越出可见区域时翻转或限制位置。
- 页面关闭、行被回收、锚点失效时关闭弹层，取消动效并清理旧回调。
- 奖励定义或图标缺失时显示明确的占位并输出定位信息，不冒用其他奖励的图标。
- 能预览不表示能发放；不支持的奖励仍由业务能力检查禁止领取。

```csharp

chestView.SetRewards(rewards);       // 沿用当前宝箱图标，只替换奖励
chestView.ShowPreview();
chestView.HidePreview();
```

- 点击宝箱展开，再次点击关闭；空列表或没有正数奖励时禁用预览按钮。
- 绑定时复制有效奖励条目，原业务列表后续变化不会修改当前预览；重新绑定会先关闭旧预览。
- 宝箱禁用时解绑自身点击回调并立即关闭提示框；再次启用不会重复订阅。
- 提示框每次显示都会刷新内容，复用已有条目并隐藏多余条目；快速开关会取消前一段缩放动画。
- 提示框内或当前宝箱上的按下不会触发外部关闭；点击其他位置关闭。原单参数 `Show` 调用仍可使用。
- 调用方使用 `Bind(Sprite, IReadOnlyList<RewardEntry>)` 或 `BindPresentation`；`RewardSlotView.Bind(RewardDataSO)` 解析数量、无限时长和宝箱外观。
- 该控件通过页面的序列化引用使用，无需新增 UIForm ID；已接入通行证奖励行，View 不包含发奖、领取进度或无限生命计时逻辑。

## 7. 方案比较与推荐

| 方案 | 优点 | 代价/问题 |
| --- | --- | --- |
| 扩充 `PropType + Count`，增加金币、无限生命、无限提示等枚举 | 首次改动小 | 资源与效果混合，类型随游戏增长，无法明确表达可选能力、单位及范围 |
| **资源定义 + 发放方式 + 按能力接入 + 旧数据适配（推荐）** | 无经济/生命的游戏也可使用；数量与无限时长共用资源，展示可复用 | 需要旧配置适配、显式能力注册和限时权益的发放/存档边界 |
| 一次性替换全部奖励配置、发奖、存档和 UI | 最终数据统一 | 影响商店、排行、首胜、连胜、任务和活动，迁移与回归成本高 |

推荐第二种，按长期维护模板设计，分为以下五个小模块：

| 模块 | 职责 |
| --- | --- |
| 静态奖励配置 | 资源定义、奖励包、显式作用域和合法输入 |
| 解析与展示转换 | 旧数据适配、数量/时长格式化、单项/宝箱选择 |
| 发奖与限时权益规则 | 完整验证、可靠入账、时长累加与去重；纯 C# 规则 |
| 游戏接收与使用适配 | 各游戏自己的库存、生命扣除点、限时能力和存档 |
| UI 视图 | 展示、预览、剩余时间刷新；业务页面另行发起领取 |

装配继续使用现有配置预加载、`GameManagerComponent.InitializeSubGames` 和游戏 `InitializeModule(SaveDataStore)`；依赖通过明确的对象引用/接口传入。界面订阅业务结果，不从动画回调发奖，不增加全局奖励 Manager。具体游戏资源、配置和存档留在自己的目录。

实施顺序建议：

1. **第一阶段：数据和展示兼容（已接入）。** 扩展 `RewardDataSO`，新增资源定义、条目和解析适配，接入现有奖励 View，补充配置验证与迁移检查。旧资产继续可读；新限时奖励在真实接收器准备前只可配置/预览，不宣称已经能发放。
2. **第二阶段：可靠发奖和实际消费。** 明确接收/存档提交边界，接入权益持久化及游戏的道具/生命扣费点，再启用对应领取能力。此阶段必须处理 3.6 的重复与部分提交风险。
3. **后续页面逐步接入。** 通行证等来源使用同一数据和展示入口，按页面迁移并回归。现有商店去广告、任务解锁等维持原语义，按需要另外设计。

现在确定上述数据和触发规则。随机宝箱、自动估值、可用后再激活的兑换券、永久无限奖励、任意 Buff 系统及服务端经济系统不在本轮实现范围。
